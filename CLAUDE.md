# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Polyfish is an AlphaZero-style AI (MCTS + neural network) that plays *The Battle of Polytopia*. The core is a from-scratch reimplementation of the entire Polytopia game engine — first written in TypeScript, then ported to Rust (`polyfish-rs/`) for performance and training throughput. Everything of consequence lives in `polyfish-rs/`; the root directory is Node-based glue (server launch wrappers, Telegram/Supabase reporting) plus the satellite data-capture projects.

## Repository layout

- `polyfish-rs/` — Rust game engine, AI, web backend, and all training code. This is where ~all work happens.
- `src/public/` — the static web UI (JS/HTML/CSS): the simulator (`index.html`) and the training dashboard (`training.html`), and the only copy of either. No build step; the `polyfish` binary serves it at `/simulator/*` and as the fallback for `/`.
- `polyfish-ui/` — newer Vite/TypeScript UI. The server serves its `dist/` build at `/`, `/assets` and `/static`; `dist/` is gitignored and the build needs Node ≥20.19 (vite 8), so a fresh clone gets the `src/public` UI until you run `npm install && npm run build`. It no longer forks the static UI (#55) — it iframes `/simulator/index.html` and `/simulator/training.html`, which the server mounts from `src/public`. The four `ServeDir` paths live in `polyfish::web_static` so tests assert on the same constants the server reads.
- `polyfish-mod/` — C# mod (BepInEx/PolyMod) that runs inside the real Steam game to auto-play replays and POST captured game states to the local server.
- `polyfish-scraper/` — TypeScript utilities for gathering game data/assets.
- `polyfish-reader` — the C++ process-memory ripper. **Not checked into this repo**; `scan.sh` compiles and invokes it against a running `Polytopia.exe`.
- `*.py`, `*.sh`, `*.js` at root and in `polyfish-rs/` — training, analysis, and reporting scripts.

## Commands

All `cargo` commands run from `polyfish-rs/`. The root `run-server.sh` and `polyfish-rs/run_training_loop.sh` `cd` there for you.

**Run the web server / simulator** (port 3000; serves `src/public` at `/` and `/simulator/*`, plus `polyfish-ui/dist` if you have built it):
```bash
./run-server.sh                      # from repo root; kills :3000, then `cargo run --bin polyfish`
```
On startup `main.rs` tries to load game state from `live_game.json`, `saved_state.json`, then the newest canonical `replays/*.replay.json`, before falling back to a generated map. Pre-canonical mod captures (`mod_replay_*.json`) are no longer read directly — `/replay/save` converts them on the way in and `import_replays convert-legacy` migrates an archive offline (#41). Every replay name — both save endpoints, the Supabase storage key, and the filters the loader, `import_replays` and `upload_replays` read with — comes from `src/replay/paths.rs`, so a producer can no longer write a name its consumers ignore (#45).

**Build the training binaries** (release is required for any real training):
```bash
cd polyfish-rs && cargo build --release --bin polyfish --bin self_play --bin arena
```

**Tests** (`Cargo.toml` declares no `[[bin]]` sections and no `test = false`, so every `src/bin/` target is auto-discovered and testable — the gate simply names `--bin self_play` and no other. `#[ignore]` marks heavy probes and measurement tools, which CI does not run):
```bash
# The main gate — note --no-default-features, which is what .github/workflows/rust.yml runs
cd polyfish-rs && cargo test --no-default-features --lib --tests --bin self_play

cd polyfish-rs && cargo test --test integration my_test_name       # a single libtest case
cd polyfish-rs && cargo test -- --ignored test_min_capital_distance_1v1   # heavy mapgen probe
cd polyfish-rs && cargo run --bin stats -- --games 50              # manual diagnostic tool
```

CI (`.github/workflows/rust.yml`) also runs, and these are worth running locally before touching what they cover:
```bash
cd polyfish-rs && cargo test --no-default-features --test parity_widths   # Rust vs train.py head widths
cd polyfish-rs && python3 scripts/check_cli_contract.py                   # shell -> binary/python-CLI flag contract
cd polyfish-rs && cargo clippy --no-default-features --all-targets        # clippy::correctness, blocking, no carve-outs
cd polyfish-rs && cargo fmt --check                                       # advisory
cd polyfish-rs && ./scripts/run_python_tests.sh                          # ladder.py + train.py (stdlib unittest)
cd polyfish-rs && ./scripts/run_forward_parity.sh                        # candle CPU vs train.py on three checkpoints
```
`.github/workflows/smoke.yml` runs `scripts/smoke_train_loop.sh` nightly (and on demand): a real one-iteration `self_play` → `games_*.safetensors` → `train.py` → `model.safetensors` pass plus an `arena` gauge reading, into a scratch dir under `target/smoke/`. That seam is where all three of the 2026 pipeline blockers hid — run it after changing `run_training_loop.sh`, `train.py`, or either binary's CLI. It also forces the anchor-freeze and audit branches, which no reading it can afford would otherwise reach (`GAUGE_FREEZE_WR=0`, `GAUGE_LINK_GAMES=1`, `GAUGE_AUDIT_EVERY=1`; `SMOKE_FORCE_FREEZE=0` turns that off) — those branches had never executed anywhere, and their first run would have been mid-campaign in a fail-fatal loop (#35). Its push-to-main path filter now also covers `src/ai/**`, `src/game.rs`, `src/moves/**`, `Cargo.toml`, `Cargo.lock` and `requirements.txt`, so a runtime-shaped break in the eval-server seam cannot merge green and sit until the nightly (#48); it still has no `pull_request` trigger, which remains a deliberate cost decision.

`.github/workflows/undo_fuzz.yml` is the second nightly (06:00, an hour after the smoke; also `workflow_dispatch`, and pushes to `main` touching `src/game.rs`, `src/actions/**`, `src/moves/**`, `src/memory.rs` or the probes). It runs `cargo test --release --test undo_integrity -- --ignored` — all four arms: legacy / adversarial / fogged `clone_for_mcts` / both — plus a rotating-seed `examples/undo_fuzz` whose start seed is `github.run_number * 200 + 1` and is echoed into the log, so a red nightly re-runs on exactly the seeds that broke it. The `--ignored` run is deliberately scoped to `--test undo_integrity`: the other `#[ignore]`d items in the tree are diagnostics and must not start running. It is a separate workflow because `on.push.paths` is workflow-wide and the smoke's opt-level-1 build is not reusable. `undo_arms_smoke` in `tests/undo_integrity.rs` is **not** ignored — it runs all four arms cheaply on the normal gate, so a broken arm reds the PR instead of waiting a day (#47).

**Python training setup** (creates `polyfish-rs/.venv` from `requirements.txt`):
```bash
cd polyfish-rs && ./local_setup.sh           # macOS/Apple silicon or plain Linux CPU
cd polyfish-rs && ./remote_setup.sh          # generic CUDA box (also installs Rust, builds release)
cd polyfish-rs && ./vast_setup.sh            # Vast.ai; additionally builds tch-eval
```
`requirements.txt` holds the shared, pinned core and **deliberately does not list torch** — each target needs a different wheel index. All three scripts read the single version pin from the `# POLYFISH_TORCH_VERSION=` line in `requirements.txt` and install the matching wheel (PyPI on macOS, CPU index on Linux, cu128 on a GPU box). Raising that pin means re-checking `tch-rs` first: `tch-eval` links against this exact torch.

**Full self-play + train loop** (the main training driver):
```bash
cd polyfish-rs && ./run_training_loop.sh [flags]
```
Short flags (getopts `fbcri:g:n:a:e:l:k:`): `-f` force-train, `-b` boost-threads, `-c` chill, `-r` reward-shaping, `-i` iterations, `-g` games-per-iter, `-n` mcts-iters, `-a` actors, `-e` eval-servers, `-l` league/gauge interval (default 10), `-k` gumbel-k. Long flags: `--resume [run_id]`, `--new-run`/`-N`, `--reset`, `--no-server`.

The loop is: `init_model.py` → `self_play` (Rust, generates `games_*.safetensors`) → `train.py` (Python/PyTorch, updates `model.safetensors`) → log a CSV row → checkpoint every 50 iters into `checkpoints/` → archive consumed games — **before** the gauge, so an aborted reading cannot leave a trained-on file in root for the next launch to re-train as fresh (#37) — plus a strength-gauge match every `-l` iterations. A failed gauge reading is now fatal — the loop aborts rather than continuing blind, which is what left an entire campaign without a single recorded reading. CUDA is opt-in via the `cuda`/`cudnn` Cargo features. `--reset` deletes `model.safetensors`, all self-play game data (`games_*.safetensors` in root and `archive/`) and `.anchor_decay_start` before starting; it forces a new run (overrides `--resume`) and leaves `checkpoints/`, `training_log.csv`, and `moves_by_turn.json` untouched. Each run is a **new run** by default; `--resume` continues the latest. A bare launch with both `model.safetensors` and `training_log.csv` history present **aborts** rather than silently rewinding every iteration-keyed schedule to 1 (10-turn Tiny curriculum, prior 0.5, value-trust ~0, anchor-frac 0.25) on a trained model — say which you meant with `--resume`, `--new-run` or `--reset` (#37). Whenever `POLYFISH_BACKUP_DIR` is set the loop also snapshots the experiment record through `scripts/backup_experiment_record.sh`: every `POLYFISH_BACKUP_EVERY` iterations (default: the checkpoint cadence, taken last in the iteration so weights and the rows grading them land together) plus once from the exit trap, so an aborted run still leaves the record. That snapshot is deliberately non-fatal — an unreachable or full target warns on stderr and the run continues — and an unset `POLYFISH_BACKUP_DIR` is announced at startup (#23).

There is no PowerShell loop any more: `run_training_loop.ps1` and the `start-hidden.vbs` → `auto_train.ps1` → `run-training.bat` chain were deleted in #56 (no gauge, ladder, anchor freeze or plateau stop, and `scripts/check_cli_contract.py` reads only `.sh`). Train on Windows under WSL2 with the sh loop; `run-server.bat` is kept and still launches the server. Root `auto_train.sh` is the Linux/GNOME idle babysitter: it starts `polyfish-rs/run_training_loop.sh --resume` under `setsid` from `polyfish-rs/` and halts with a process-group TERM, so the loop's EXIT trap runs `finish-run` and the `polyfish` server it spawned releases port 3000. `tests/test_auto_train.py` pins that contract, including that the deleted chain has not returned.

**Head-to-head evaluation:**
```bash
cd polyfish-rs && cargo run --release --bin arena -- --model1 a.safetensors --model2 b.safetensors --games 32 --mcts 64 --seed 20260811
```
Pass `--seed` for anything you intend to compare: without it `arena` seeds from the wall clock and re-rolls the map set every run.

## Architecture

### Game engine (`polyfish-rs/src/`)
- `states.rs` / `types.rs` — the `GameState` data model and all enums (tribes, units, tech, moves, etc.). `GameState` (de)serializes to/from the JSON produced by the mod and reader.
- `game.rs` — the `Game` controller: load state, run `post_load()` (recompute tile indices/visibility), apply moves, manage turns. The engine is intended to be "perfect": legal-move generation and `execute` should never panic on valid input — panics are treated as bugs to surface, not suppress. `play_move` is the real path; `simulate_move` is the in-tree path (it does not set `_are_you_sure`, so the search never reveals fog — deliberate anti-cheating, not a bug). `simulate_move`'s `EndTurn` branch is the one place the two diverge in game semantics: see the adversarial-search switch below.
- `moves/` — the `Move` trait and `generate_legal_moves(state)`. Moves split into **economy moves** (city/tech/structure — mostly keyed by `target_index`) and **army moves** (step/attack/capture/abilities — mostly keyed by `src_index`). Unit abilities live in `moves/abilities/`.
- `actions/` — lower-level reusable state mutations (gain stars, exploration, effects) that moves compose, with undo-callback support for MCTS rollouts. `tests/attack_matrix.rs` is the direct matrix over `actions::units::attack_unit` (damage arithmetic, the splash index-shift re-find, the three retaliation gates, Persist/DoubleAttack/Escape), asserting an undo round-trip on every case; `tests/capture_elimination.rs` covers capturing a tribe's last city. Two engine doubts are **pinned there as current behaviour rather than fixed**: a melee Persist kill still ends the attacker's turn (the move-in's `step_unit` sets `attacked` before the Persist branch runs, and that branch only declines to set the flag), and `capture_city`'s elimination sweep books no `kills` for the capturer (`remove_unit` credits kills only when both `killer_owner` and `killer_idx` are `Some`). Changing either alters what the agent can do in a turn, so both are EXP-registerable, not drive-by fixes (#53).
- `settings/` — static game data tables: `units.rs`, `technology.rs`, `structures.rs`, `resources.rs`, `tasks.rs`.
- `mapgen.rs`, `coords.rs`, `fow.rs`, `memory.rs`, `score.rs`, `hash.rs` — map generation, coordinate/index math, fog-of-war, observation memory, scoring, state hashing. **`score.rs` is the single scoring definition**: `breakdown` (what `functions::calculate_detailed_tribe_score` now delegates to) plus the `structure_score` / `unit_score` / `tile_score` / `city_core_score` pieces every incremental `tribe.score` mutation in `actions/` reads, so the maintained field and the recompute cannot price the same thing differently (#40). Territory and the structures on it are priced **per distinct tile the tribe owns**, not per city `_territory` entry — cities two tiles apart share entries and a stolen tile stays listed in the city that lost it, so the old per-city walk double-counted the first and mis-credited the second. `tests/score_parity.rs` asserts parity after every move on seeds picked to fail before the fix; `examples/score_parity_fuzz` is the same check at fuzz depth and ranks any drift by the move kind that caused it. **Training runs with FOW enabled** (deliberate, to avoid learning cheating/FOW-less strategies). `GameState::obscure_fog` (`states.rs`), reached only from `Game::clone_for_mcts`, is the single choke point for that: a tile the POV has never explored must carry no field that still names its owner. It clears terrain/owner/roads/effects/`_unit_owner_id` and, since #54, `capital_of`/`climate`/`ruling_city_coords`/`had_route`/`skin_type`; `tests/fow_residual_identity.rs` pins the list, so add any new identity-bearing tile field to both. Note the deliberate gap: the in-tree opponent still holds its **true** stars, tech and score — registered on EXP_SEARCH_001, not a bug to fix quietly.
- `state_fingerprint.rs` — `undo_fingerprint(state)`, the half of an undo comparison a JSON snapshot cannot see: iteration order of every `IndexMap` (load-bearing for temple growth, fungi spread, sanctuary spawns and movegen order) plus `_sim_explored`, which is `#[serde(skip)]`. Both undo probes (`tests/undo_integrity.rs`, `examples/undo_fuzz.rs`) compare it alongside the JSON; without it an entry that undo re-appended instead of restoring to its slot compares equal. Empty `_sim_explored` sets are skipped on purpose — `discover_tiles` inserts via `entry().or_default()` and its undo removes only the indices.
- `version_sync.rs` — the ruleset sync point: `GameVersion` names each Polytopia revision the rules gate on, `CURRENT_VERSION` (= `GameVersion::CymantiRework`, 115) is the single constant `GameSettings::default()`, its serde default and `MapGenSettings::default()` all read, and `is_at_least` / `is_before` are how engine code compares a version. Do not reintroduce a bare numeric comparison: `GameSettings::default()` sat at 1 while every generated map ran 115, so any default-state test of a version-gated rule silently asserted Aquarion-era rules (#51). `GameVersion::Legacy = 0` is the pre-versioning value scraper data pins explicitly — `features.rs`'s `version <= 0` normalization scales and the explicit-zero inserts in `main.rs` and `bin/validate_csv.rs` depend on it staying 0. `tests/default_version.rs` pins all of this. The **training-import** version range deliberately does not live here; see `replay/validator.rs`.
- `replay/` — the replay subsystem (`schema.rs`, `command.rs`, `loader.rs`, `executor.rs`, `playback.rs`, `validator.rs`, `verify.rs`, `outcome.rs`, `legacy.rs`, `paths.rs`, `recorder.rs`, `training.rs`). Distinct from the top-level `recorder.rs`, which records human/mod steps for imitation data. Five parts carry traps:
  - `validator.rs` owns the **supported game-version range** for training import: `MIN_SUPPORTED_GAME_VERSION` (105) to `MAX_SUPPORTED_GAME_VERSION` (= `version_sync::CURRENT_VERSION`, so the ceiling follows the newest ruleset the engine implements). `validate_training_eligibility` refuses a replay outside it — a capture from a ruleset Polyfish does not have is re-derived under today's rules, so every exported sample is mislabelled while every command still looks legal. `import_replays --allow-version-drift` downgrades the refusal to a warning (#44).
  - `outcome.rs::derive_result` synthesizes a `ReplayResult` for a capture that carries none (the mod's serializer emits no winner key), from the executed final state: survival decides first, and score breaks only a genuine turn-limit terminal, and then only among the living — the same rule as `ai::mcts_common::compute_terminal_outcome`, deliberately duplicated because the in-tree version answers per-player, can express a partial tie a single `ReplayResult` cannot, and sits on the search path. It is gated on `functions::is_game_over` and refuses a non-terminal state, so a truncated replay can never become a score-proxy teacher label (the A2b/#38 extension). Derived labels are marked: `reason` gets a `derived:` prefix and `DatasetManifest` lists them under `derivedResultSourceFiles` (#42).
  - `legacy.rs` is the one authority for the C# mod's pre-canonical capture payload: it drops Nature (255), repairs `currentPlayerTurnId` (the source writes a 0-based seat index there, not a player id), drops `moveType -1`/`11` rather than translating them, and walks the engine so segment turn/player counters are engine-sourced. It deliberately tolerates the source snapshotting *after* the game's own forced opening — at most `MAX_PRE_APPLIED_COMMANDS` (2) leading commands the captured state already reflects are skipped, counted and named in `metadata.sourceDiagnostics`. Do not "fix" `UpgradeMove::serialize` to emit an `upgrade` key without updating this file: the converter relies on `Summon` matching both `SummonMove` and `UpgradeMove` (#41).
  - `verify.rs`'s `DivergenceVerifier` cross-checks engine state against `metadata.sourceDiagnostics.endTurnCheckpoints` before each EndTurn — before, not after, because `Game::end_turn` advances the player and pays income in one call. `stars`/`unitCount` hard-fail; `score` is reported only, since `tribe.score` is a known-drifting incremental. It is inert until a capture source writes those checkpoints, and none does yet (#44).
  - **`ReplayExecutor`'s ambiguity rule.** Multiple legal moves matching one command are an error only when they are *genuinely distinct*: `generate_legal_moves` walks a tile once per city whose territory contains it, so a tile inside two of a player's territories yields the same Build/Harvest move twice, and `executor::all_indistinguishable` collapses identical matches while keeping `AmbiguousCommand` for the rest. `Debug` is the identity, deliberately — `SummonMove` and `UpgradeMove` share `MoveType::Summon` and serialize identically, so a `serialize()` comparison would have merged them. The duplicate movegen itself is unfixed: deduplicating legal moves changes search priors and policy targets, so it needs a registered experiment (#43; open item in the audit).

  `tests/replay_round_trip.rs` is the command-matrix guard: a network-free driver plays a real engine game, records it, round-trips it through `save_replay`/`load_replay` and re-executes it, asserting **per command** that the executor resolves the same move the driver played — a final-state-only check masks `matches_move` picking a different legal move that merely satisfies its predicate. It reaches 10 of the 12 `ReplayCommand` variants and fails if it stops reaching any of them; the other two are unreachable by construction (no `Move::serialize` emits the `"upgrade"` key `from_move` and `matches_move` key on, so `ReplayCommand::Upgrade` is dead, and `generate_legal_moves` never emits a `ResignMove`). When comparing replayed state, `_messages` must be cleared (the executor clears it after every command, `play_move` does not) and the `HashSet`-backed arrays (`explorers`, `effects`, `builtUniqueImprovements`, `knownPlayers`) sorted; every other array order is real state.

### AI (`polyfish-rs/src/ai/`)
- `mcts_zero.rs` — the AlphaZero-style MCTS (`ZeroMctsAgent`). `gumbel_mcts.rs` is the Gumbel variant and the one training actually uses; `heuristic_mcts.rs` is a network-free MCTS for fast UI analysis and the interactive trainer. `mcts_common.rs` holds the shared backup/descent logic; `original_mcts_zero.rs` is an older implementation — check whether a change needs to land in more than one. `mcts.rs` is gone (#57): its `MctsAgent` was constructed nowhere and drew from the thread-local RNG, and its three analysis structs moved verbatim into `heuristic_mcts.rs` (field names untouched — they are the serde wire contract the UI's move-evaluation overlay reads). A re-audit of adversarial sign handling therefore finds two sites, not the three `expert_pipeline_audit.md` records; the deleted `uct_select_child` was one of them.
- **Two backup conventions, deliberately.** `mcts_common::backpropagate_and_remove_virtual_loss` stores each node's value in **its own player's** perspective (used by `mcts_zero`), while `backpropagate_return_with_rewards` stores the action value of the edge into the node, i.e. the **parent's** perspective (used by `gumbel_mcts`). Both are self-consistent; each agent's child-selection rule has to match its own convention — `mcts_zero` negates a handover child before comparing siblings (`effective_value_for_parent`), Gumbel compares `q_value()` directly. Get this wrong and the parent picks the move that is best for the opponent. `mcts_common::edge_hands_over` is the shared "does this edge change the mover" test.
- `brain.rs` — top-level agent wiring. `Brain::with_backend(...)` plus the `with_prior_heuristic_weight` / `with_policy_target_q_weight` / `with_tree_q_weight` builders decide what the agent actually is. `arena.rs` threads all three; both binaries also search a fog-obscured `clone_for_mcts` view. The schedules that set them live in `ai/curriculum.rs` — self-play applies them, `arena` falls back to `CONVERGED_*` for a hand-run with no iteration in hand, and the gauge is passed the iteration's actual values (see below), so a new knob has to be added to the shared module rather than mirrored. `max_turns_ahead` here is the in-tree turn horizon (`MIN_TURNS_AHEAD` / `MAX_TURNS_AHEAD`).
- `network.rs` — `PolyZeroNet`, the candle network: player-state embedding + ResBlocks + cross-attention + a **decomposed policy** and a value head (two outputs: `v_win` and `v_progress`).
- **`v_progress` is trained but deliberately unread by the search.** It is a real head — `network.rs`, `train.py`'s MSE on the `progress` target, the target written by `self_play` — but nothing in `gumbel_mcts`/`mcts_zero` consumes it. It used to be added into `GumbelNode::q_value()` — which reaches both labels, since the root q_value is the TD bootstrap for the value label and `extract_policy_targets` builds π′ from the children's q_values. Since only candle computes the head (tch and metal stub it to 0), that made training data depend on which backend generated it; it also mis-signed the opponent's progress under adversarial search, and, being `0.0` on unexpanded children, biased π′ toward whatever the search expanded. Do not fold it back into Q without implementing it in all backends *and* negating it across handover edges (EXP_LABEL_002; `tests/test_progress_head_not_in_search.rs` fails if you do).
- `features.rs` — encodes `GameState` into the input tensor. Key constants: `MAP_SIZE = 11`, `NUM_CHANNELS`, `RawFeatures::PLAYER_STATE_DIM`. Maps are 11×11. **The absolute channel layout is pinned**, the same way `mapper.rs` pins the action head, because the four `*_INDEX` tables are `Enum::iter().enumerate()` over declaration order in `types.rs` — so a mid-enum insertion shifts every later channel and silently garbles every trained checkpoint and every archived `games_*.safetensors`. Four pins: a `const _` block after `NUM_CHANNELS` asserts every block start (`CH_TERRAIN_START == 0` … `NUM_CHANNELS == 142`) at compile time; `channel_slots_are_stable` pins all 98 enum slots and all 42 named flag/stat channels to literals; `no_enum_variant_escapes_its_block` fails if any `*_COUNT` is outgrown; and `tests/feature_encoding_golden.rs` holds a per-channel FNV-1a digest of `state_to_cpu_features` on a fixed mapgen seed so encoding-*semantics* drift fails too — it asserts a separate `MAP_FINGERPRINT` first, so a mapgen re-roll and a real layout regression report differently (#46).
- `mapper.rs` — `DecomposedMapper` / `DecomposedTargets`: the policy is decomposed into four heads — `action_type`, `source_spatial` (H·W), `target_spatial` (H·W), and a unified `move_option` (192, with offset blocks for structures/units/techs/abilities). This decomposition exists because raw legal-move ordering is non-deterministic across states, so moves are mapped to stable semantic coordinates instead of a flat action index.
- `evaluator/` — heuristic state evaluation split by concern: `economy.rs`, `army.rs`, `research.rs`, `exploration.rs`, `expansion.rs`, `gamestate.rs`, `player.rs`. Used to shape/guide self-play and for non-NN play.
- `reward.rs` — the shared per-move reward used by both TD value labels and reward-aware MCTS backup. `reward::REL_W` is now the **single** relative-vs-absolute constant, read by both the TD body and self_play's final-outcome tail (`self_play.rs`'s separate `FINAL_OUTCOME_REL_W` is gone). It is 1.0 = pure relative, because the backup negates across every player-turn boundary and that is only valid for an antisymmetric value. Read the comment block on the constant before lowering it; `GOOD_BOT_FINAL_SCORE` is the absolute yardstick it would reintroduce.
- `book.rs` — opening-move library, **data only: no search agent reads it**. It used to hard-force a uniform-random pick on game turns 0–1 and fabricate the matching policy target (a one-hot in `mcts_zero::select_move_with_stats`, a single full-iteration-count `MoveVisit` in `select_move_with_decomposed_visits`) and to replace every node's untried set in `heuristic_mcts`; #57 retired all four call sites and `tests/test_book_not_forced.rs` fails if any comes back. The table and `tests/verify_opening_book.rs` stay. `ordering.rs` — move ordering; `policy_composer.rs` — assembles head outputs into a move distribution; `decision_trace.rs` — search introspection.

### Inference backends
Four implementations read the same `model.safetensors`, selected by Cargo feature:
- `network.rs` (candle) — default, and the only one on non-Apple hardware.
- `tch_network.rs` (`tch-eval`) — libtorch/MPS. Requires PyTorch 2.12.x plus `LIBTORCH_USE_PYTORCH=1`, `LIBTORCH_BYPASS_VERSION_CHECK=1`, and `.venv/bin` on `PATH`; see the comments in `Cargo.toml`.
- `metal_network.rs` (`metal-eval`) — hand-composed MPSGraph, bypassing libtorch's serial MPS dispatch queue. Fastest on Apple silicon.
- `eval_backend.rs` / `eval_server.rs` — the batching layer that fans leaf evaluations across actors.

`examples/tch_parity.rs` and `examples/metal_parity.rs` exist to check backends against each other — run them after any architecture change. Neither runs off Apple hardware; **`polyfish-rs/scripts/run_forward_parity.sh` is the one that does** (candle CPU vs `train.py`'s PyTorch on the same `model.safetensors`, CI job `forward-parity`). Run it after touching `network.rs`, `train.py`, `features.rs` or `mapper.rs`. It compares **three** checkpoints, not one: the base, a seeded perturbation that moves every GroupNorm affine off 1 and every bias off 0, and a synthesized legacy checkpoint put through `train.py`'s `_migrate_checkpoint` — both built by `scripts/make_parity_fixtures.py` and unit-covered by `tests/test_migrate_checkpoint.py`. CI's base is always a fresh `init_model.py` checkpoint, whose affines sit at identity and whose biases are zero, so on it alone affine/bias mapping drift is numerically invisible: dropping every affine and bias from that checkpoint changes its outputs by exactly 0.0, and the perturbed fixture by ~9 (#48). `examples/tch_parity.rs` now also *runs* on the macOS `tch-eval` CI row (advisory, after an `init_model.py`) — the first execution of a non-candle backend anywhere in CI — and because `metal_parity`/`metal_bench` carry required-features on **both** `metal-eval` and `tch-eval`, a combined-features matrix row exists purely so `--all-targets` stops silently skipping them.

⚠️ **candle and strided tensors.** `candle_nn::Linear` on a non-contiguous 3-D input returns wrong values for every batch row after the first — by position, not contents. `network.rs` hit this on the cross-attention query tokens and every batched evaluation on the default backend was corrupted for all but one row (see audit T1). Call `.contiguous()` on anything that reaches a matmul after a `transpose`. A batch-invariance test does **not** catch it; only an oracle outside candle does.

### ⚠️ The multi-implementation sync constraint
The network architecture is implemented in **Rust (candle) and Python (PyTorch)** and must stay byte-compatible because they read/write the same `model.safetensors`:
- Rust: `polyfish-rs/src/ai/network.rs` — used by `self_play`, `arena`, the server, and the Rust `train` binary.
- Python: `polyfish-rs/train.py` — the primary trainer used by `run_training_loop.sh`; `init_model.py` creates the initial weights from this definition.

If you change layer shapes, channel counts, or head sizes in one, you must mirror it in the other (**and** in `tch_network.rs` / `metal_network.rs`, and in `features.rs` / `mapper.rs` constants). Current values: spatial channels **142** (`features.rs` `NUM_CHANNELS`, `train.py` `SPATIAL_CHANNELS`; = 136 + 6 fog-memory channels), player-state dim **16** (`features.rs:216`, `train.py` `PLAYER_STATE_DIM`), map 11×11, 6 ResBlocks on a 64-filter trunk, policy heads = action + source + target + option(192), normalization = GroupNorm(`GN_GROUPS = 8`) — no BatchNorm anywhere; the 1-channel pool convs are fully linear (no norm, no activation, since an unnormed ReLU there dies irreversibly). Mismatches surface as safetensors load errors or silent garbage. Legacy 136-channel training data is zero-padded at load by `train.py` (`pad_spatial`, channels were appended at the end of the layout), as are pre-widening 11-column `action_type` targets; BatchNorm-era checkpoints are rejected by `migrate_model.py:25-30`.

**Resolved trap, kept as context:** `network.rs` used to export `NUM_ACTION_TYPES = 12` for the self-play/replay writers while building `pi_action` with a hardcoded `11` in both `network.rs` and `train.py` — so every target the writers produced was one column wider than the head, because `mapper.rs` maps `MoveType::Resign → 11`. Both sides now derive from the constant (`network.rs:10`, layer at `:227`; `train.py:96`, layer at `:165`), a const assertion keeps `Resign` inside the head (`network.rs:20`), and `tests/parity_widths.rs` fails the build if the Rust and Python widths ever disagree again. Add the same kind of assertion for any new width you introduce. Note `ResignMove` is still never emitted by `generate_legal_moves`, so slot 11 gets no self-play gradient — widening the head did not make resignation learnable. The same trap had a second home in the training-data **writers**: `replay/training.rs`, `recorder.rs` and `self_play.rs` each held a literal `192` for the option head, outside `parity_widths.rs`'s net, so a coordinated head change would have passed parity while the writers emitted stale-width files. All three now read `mapper::NUM_MOVE_OPTIONS`, and `tests/test_writer_widths.rs` fails the build if a literal comes back (#45).

**Second resolved trap, same shape, on the input side:** `TerrainType` gained `Wetland = 7` and `Mangrove = 8` while `features.rs`'s `TERRAIN_COUNT` stayed 8, so `terrain_to_channel(Mangrove)` returned channel 8 — which is `CH_TILE_FROZEN`, the first channel of the *next* block. Every check stayed green; they only asserted block ordering, `idx < COUNT` and that the counts sum to `NUM_CHANNELS`. Only JSON-loaded states (mod / reader / replay) can carry a Mangrove tile — mapgen writes only Ocean/Field/Forest/Mountain/Water — so no training data was affected. A private `slot()` helper now folds any out-of-block index onto its block's `None` slot, and `no_enum_variant_escapes_its_block` fails if a `*_COUNT` is outgrown again. **A `*_COUNT` cannot simply be widened**: `NUM_CHANNELS` would go 142 → 143 and `train.py`'s `pad_spatial` only recovers channels appended at the *end* of the layout, so giving Mangrove a real channel means appending one at 142, not growing the terrain block — and mirroring 143 into `train.py`, `init_model.py`, `network.rs`, `tch_network.rs` and `metal_network.rs` (#46).

**Exception:** the auxiliary head `v_ownership` (`train.py:186` — a 1x1 conv predicting end-of-game per-tile ownership, small-weight MSE, purely to densify trunk gradient) is training-only and deliberately NOT mirrored in Rust — every Rust backend loads weights by name and ignores the extra key. Do not add it to `network.rs`, and never save `model.safetensors` from `src/bin/train.rs` (candle `VarMap::save` strips them; it saves to `model_candle.safetensors` instead).

### Runtime switch: adversarial in-tree search
`game::adversarial_search()` decides whether an in-tree `EndTurn` hands control to the next player (adversarial) or cycles straight back to the mover, deleting the opponent's turn (the legacy single-player behaviour). **Default off.** Enable with `POLYFISH_ADVERSARIAL_SEARCH=1`, `game::set_adversarial_search(true)`, or `arena --adversarial`; it is process-wide and read on every in-tree `EndTurn`, so tests that touch it must serialize. With it on, `clone_for_mcts` also confines the in-tree opponent to the root player's vision, so the opponent it searches against is a belief-state army, not the real one. Nothing in `run_training_loop.sh` sets it — it is an unmeasured arm, registered as EXP_SEARCH_001.

### Training-only environment switches
`train.py` reads several env vars that materially change training and are set by the shell driver, not by any config file. Check these before diagnosing a training result:
- `DETACH_VALUE_TRUNK` — shields the trunk from value-loss gradient (a bisect arm, not a normal setting).
- `VALUE_LOSS_WEIGHT`, `OWNERSHIP_LOSS_WEIGHT` — head weighting.
- `AUGMENT_D4` — D4 symmetry augmentation; implemented, off unless explicitly exported.
- `TRAIN_EPOCHS`, `LEARNING_RATE`, `BATCH_SIZE`.
- `TRAIN_HOLDOUT_FRAC` — fraction of the buffer withheld from fitting to give `value_r2_holdout` (default 0.15). The split is by file and keyed on a hash of the basename so membership is stable for a file's whole life in the buffer; it runs over fresh + archive self-play only — `teachers/games_*.safetensors` always train, since they never rotate out and a permanently withheld teacher would also put static positions into the holdout reading (#36).

`bisect_arm.sh` is where diagnostic arms belong; anything exported unconditionally from `run_training_loop.sh` is a production setting.

### Binaries (`polyfish-rs/src/bin/`)
26 binaries; the load-bearing ones:
- `self_play.rs` — generates training games (`--num-games`, `--mcts-iters`, `--tribe1/2`, `--opponent <checkpoint>`, `--anchor-frac`, `--value-trust`, `--reward-shaping`, `--iteration`, `--decay-last-iter`, `--anchor-decay-start`, `--symmetric` (default true), `--opening-temp-moves` (default 8), `--print-curriculum`); emits `METRICS:` JSON lines parsed by the loop script and writes `games_*.safetensors`. Its high-score recap goes out through `replay::save_replay` (creating `replays/high_scores/` first), so every iteration validates one canonical replay for free; a validation failure warns rather than aborting, since `games_*.safetensors` is already written by then (#43). Also owns the value-label definition and the curriculum — `--print-curriculum` is how other tools ask for it instead of mirroring its thresholds.
- `arena.rs` — battle two configurations head-to-head (`--model1 --model2 --games --mcts --backend1/2 --seed --max-turns --dump-stats-dir --symmetric --adversarial --tribe1/2`). Plays each seed twice with sides swapped; `--seed` pins the map set so readings are paired, and `--tribe1/2` (default an Imperius mirror) pins the tribes — the swap pairs the tribe alongside the seat, and arena prints the pair it played on a `Tribes:` line so callers record the match rather than their intent.
- `train.rs` — Rust/candle trainer (alternative to `train.py`).
- `trainer.rs` — interactive CLI to play against the AI and correct its moves.
- Diagnostics: `benchmark.rs`, `actor_ceiling.rs`, `compare_evaluators.rs`, `repro_loop.rs`, `validate_csv.rs`, `stats.rs`, `debug_*.rs`, `verify_*.rs`.
- Replay management: `import_replays.rs` (`validate` / `export-training` / `convert-legacy`), `upload_replays.rs`, `download_replay.rs`, `extract_versions.rs`.
- Destructive one-shots: `delete_all_replays.rs` (empties the storage bucket and the games table) and `unverify_all.rs` (clears `verified` on every games row). Both print the resolved URL, bucket and object/row counts, take `--dry-run`, and refuse to act without a typed confirmation or `--yes`, exiting 1 when there is no terminal to ask on — the bucket holds the scarcest data in the project, since each pro replay needs the Steam game physically re-played. Their shared env resolution, row counting and confirmation gate live in `src/supabase.rs`; `tests/test_supabase_guard.rs` unit-tests the gate (#45).

Any binary invoked by a shell script forms a **CLI contract with that script**, and so does any python CLI beside it (`ladder.py`, `training_log.py`). `scripts/check_cli_contract.py` checks both in CI now (it builds the binaries and diffs every long flag the shell scripts pass against that target's `--help` — per subcommand for the python ones — and fails closed on anything it cannot resolve), but still grep `run_training_loop.sh` when you rename or remove an argument — three such breaks once stopped the pipeline running at all. `auto_train.sh` is in the checker's map with an empty binary set: it drives the loop, not a binary, so its contract is the loop's flags (`--resume`), pinned by `tests/test_auto_train.py`.

### Strength measurement
Separate from the training metrics, and the instrument every experiment depends on:
- `arena` plays the matches; `ladder.py` owns `ladder.json` (frozen anchors, gauge readings, freeze/plateau verdicts); `elo.py` fits ratings from those readings against the Elo-0 greedy floor. The loop refits it after **every** reading (`refit_elo` in the gauge block) into `elo_ratings.json`, which `/api/elo-ladder` serves under a `ratings` key beside the per-reading `elo_est` the chart still draws. That refit is deliberately non-fatal — the fit is derived data, recomputable from `ladder.json` at any time, unlike the reading itself, which aborts the run. A player in the fit is (run, model, **search budget**) on the same `(mcts, gumbel_k, max_turns)` key `_budget_key` uses, so two readings taken at different budgets are never chained as one player; `link` readings are exempt on purpose, because a link match is what gives a frozen anchor its identity and tagging it would strand every later reading taken at another budget in a disconnected component. `elo.py` prints a stderr note naming the span when a ladder holds more than one budget (#8).
- **A reading taken with `--dump-stats-dir` also carries a `paired` block.** `ladder.py._paired_from_stats` reads arena's per-game dumps per *seed* rather than per game, keeping the seeds that still hold both halves of their side swap, and scores each pair from the model's side. The seed is the unit of evidence the seeded map set actually buys — the map's gift to a seat cancels inside the pair — so the interval comes from the sample variance of the per-seed scores, not from a binomial on 2N games. It is **recorded only**: both the freeze bar and the plateau rule are EXP-registered tests on the unpaired counts and neither reads it (`tests/test_ladder.py::PairedReadingTest` pins that a reading with a dump and one without give the same action, win rate, interval and Elo). `rho` is the within-seed correlation the swap left behind; `required_games(..., rho=)` and `ladder.py power --rho` size a budget on it (the same evidence costs `(1 + rho) ×` the games), with rho=0 the default so the ~571-game figure the registered bars were sized against is unchanged. `ladder.py paired --stats-dir DIR` re-reads any retained dump offline. No gauge run has produced a dump yet, so `rho` itself is unmeasured (#6).
- `run_training_loop.sh` runs a gauge match every `-l` iterations against the ladder's active anchor, records the reading, and can freeze a new anchor or stop the run (plateau). A freeze needs the reading's Wilson lower bound to clear 80%. The plateau gate is EXP 11's registered rule — pooled window halves flat-or-down **and** least-squares slope ≤ 0, both directional, so a climb the gauge cannot yet *prove* no longer counts as a plateau (#31; the interval-overlap test it replaced struck on every climb below ~12pp). Its window is scoped to the current `run_id` and to the reading budget, which includes `max_turns`; strikes reset on a run change. A failed reading aborts the run.
- The gauge pins its map set (`--seed`) and asks `self_play --print-curriculum` for the iteration's `max_turns` **and its search knobs** (`prior_heuristic_w`, `policy_target_q_w`), passing them to `arena`. Both ramp over a run — prior 0.5 → 0.1 → 0, σ(Q) 0 → 1 — so a gauge on the converged constants graded a searcher self-play never used for the first ~30–53 iterations (#32). The knobs are recorded on each reading but deliberately **not** in `ladder.py`'s `_budget_key`: they change every iteration by design, so keying on them would leave the plateau window permanently empty.
- **The gauge's tribe pair is pinned (`arena --tribe1/--tribe2`, default an Imperius mirror) while self-play trains on config.json's 5-tribe pool.** The pin is variance control — the tribe block effect rivals a campaign's whole measured improvement — but it means every ladder Elo is a statement about Imperius-vs-Imperius play, not about the distribution training optimizes. That scope limit is recorded in `ladder.json`'s `scope` field, and the pair is read back off `arena`'s own `Tribes:` line rather than assumed, so the record can never again disagree with the match it describes (#34: the ladder was handed the shuffled *training* pair for a match `arena` hardcoded to Imperius). A `--kind tribe_audit` row at the audit cadence re-reads the active anchor on the iteration's training pair; it is a cross-check only — excluded from the plateau window (`_gauge_series`) and from the Elo fit (`elo.py`'s `EXCLUDED_KINDS`), since its games share a node pair with the pinned reading and would fold the block effect straight back in.
- **The freeze and audit branches are reached only from `run_training_loop.sh`**, so they are exercised nowhere else: the smoke forces them (above), `tests/test_ladder.py`'s `ShellCommandLineTest` runs `freeze` / `audit-opponents` / `record --kind audit|tribe_audit` as subprocesses with the flags read back off the loop script, and the CLI contract check covers the flags statically. An audit cadence landing on a freeze iteration plays every cross-check against the *outgoing* anchor, so those rows pass `--opponent` explicitly rather than letting `ladder.py` assume the active one (#35).
- `.anchor_state.json` / `.anchor_decay_start` persist anchor-gate state across invocations. `ladder.py`'s three env reads (`LADDER_FILE`, `GAUGE_FREEZE_WR`, `GAUGE_MIN_EFFECT`) are contract-tested by `tests/test_ladder.py`'s `EnvContractTest`, which additionally pins `GAUGE_FREEZE_WR` to the name `scripts/smoke_train_loop.sh` exports — renaming it would silently restore the production 0.80 bar inside the smoke and fail on a confusing verdict rather than a named error (#48).
- Both `self_play` and `arena` default `--symmetric` to true, and `run_gauge_match` passes it explicitly (`GAUGE_SYMMETRIC`), so the ladder reads the same map family training generates. **Known gap:** a ~64-game reading still only resolves to about ±12pp — `ladder.json` stores the interval, so use it rather than the point estimate.

### Data flow
Steam game → `polyfish-mod` (C#) / the C++ reader → JSON game states (`live_game.json`, `replays/`) → loaded by `polyfish` server or the replay subsystem. The mod still POSTs the pre-canonical payload shape; `/replay/save` and `/replay/save-local` convert it (`replay::legacy`) and write canonical `replays/*.replay.json`. A body either endpoint refuses is quarantined verbatim at `replays/rejected/<name>_<ts>.rejected.json` with the reason beside it and the path in the response, so a capture session is never lost to a rejection; `import_replays convert-legacy --input <file|dir> --output <dir>` puts a quarantined body or an archived capture back into canonical form (#41). Separately, `self_play` → `games_*.safetensors` → `train.py` → `model.safetensors` → `checkpoints/`. Training metrics go to `training_log.csv` (canonical store, keyed by `run_id` per training campaign) plus a `moves_by_turn.json` sidecar; `run_training_loop.sh` uses `training_log.py` to parse METRICS and append rows. `training_log.csv` and `ladder.json` are **tracked in git** (they are the experiment record); `checkpoints/` is not — `scripts/backup_experiment_record.sh` snapshots all of it to another disk or a remote, and the training loop now calls it (see the loop section above). Live dashboard: `http://localhost:3000/training.html`, the same file as `/simulator/training.html` — that is the path `polyfish-ui` iframes (Chart.js, reads `/api/runs`, `/api/training-metrics`, `/api/moves-by-turn`, `/api/value-distribution`, `/api/elo-ladder` from the Rust server; `/api/elo-ladder` returns `ladder.json` plus, under a `ratings` key, the git-ignored `elo_ratings.json` the loop refits). `/api/training-metrics` and `/api/runs` are both served by the single header-driven CSV reader in `training_api.rs` that both binaries route to, so a column added to the CSV reaches the dashboard without a Rust change. There is deliberately only one reader: the copy-pasted pair in `main.rs`/`bin/dashboard.rs` and the fixed-struct `MetricRow` reader that dropped 23 columns are gone (#23).

`training_metrics_schema.sql` + root `telegram_agent.js`/`run_analysis_now.js` push progress to Supabase/Telegram; run them from the repo root as `npm run agent` (the watcher daemon) and `npm run report` (one shot), both reading `./polyfish-rs/.env`. The root `package.json` declares exactly the two packages those files import, `@supabase/supabase-js` and `dotenv` — it was a 142-entry flattened transitive dump missing `@supabase/supabase-js` itself until #57, so the documented path could not run at all. But the Supabase `training_metrics` table has had **no writer** since #56 deleted `run_training_loop.ps1`, which was the only one anywhere in the repo (`run_training_loop.sh` and `training_log.py` never wrote it), so `telegram_agent.js`'s realtime listener is dormant and `run_analysis_now.js` — which reads `polyfish-rs/training_log.csv` directly — is the live reporting path. Both still shell out to an `agy` CLI that no setup script installs. `session.log` is a raw debug transcript only.

- **Inline comments:** one line; two lines is rare and needs a strong reason.
